# File & Folder Structure Requirements

## React + TypeScript Scalable Project Architecture

**Document Version:** 1.0
**Last Updated:** November 2025
**Target:** Enterprise-grade, maintainable, and scalable project structure

---

## 🎯 Executive Summary

This document defines the complete file and folder structure requirements for a scalable React + TypeScript project. The structure follows industry best practices, separates concerns effectively, and ensures test files are co-located with source code for better maintainability.

---

## 📐 Core Principles

### 1. **Co-location Strategy**

- Test files live alongside the code they test
- Related files are grouped together
- Reduces cognitive overhead when navigating the project

### 2. **Feature-Based Organization**

- Group by feature/domain, not by file type
- Each feature is self-contained and modular
- Enables independent development and testing

### 3. **Clear Separation of Concerns**

- Shared code in dedicated directories
- Domain-specific code in feature folders
- Infrastructure code separated from business logic

### 4. **Scalability First**

- Structure supports growth from 10 to 10,000 files
- Easy to split into micro-frontends if needed
- Clear patterns for new developers to follow

## 📝 Detailed Requirements

### 1. **Component Structure Requirements**

#### 1.1 Component Folder Pattern

Every non-trivial component MUST follow this structure:

```
ComponentName/
├── ComponentName.tsx          # Component implementation
├── ComponentName.test.tsx     # Unit tests (co-located)
├── ComponentName.stories.tsx  # Storybook stories (if using Storybook)
├── ComponentName.module.css   # Component styles (if not using Tailwind only)
├── types.ts                   # Component-specific types
├── hooks.ts                   # Component-specific hooks (optional)
├── utils.ts                   # Component-specific utilities (optional)
└── index.ts                   # Public API (barrel export)
```

**Example:**

```typescript
// Button/Button.tsx
export function Button({ children, variant = 'primary', ...props }) {
  return <button className={cn(buttonVariants({ variant }))} {...props}>{children}</button>
}

// Button/Button.test.tsx
import { render, screen } from '@testing-library/react'
import { Button } from './Button'

describe('Button', () => {
  it('renders children correctly', () => {
    render(<Button>Click me</Button>)
    expect(screen.getByText('Click me')).toBeInTheDocument()
  })
})

// Button/index.ts
export { Button } from './Button'
export type { ButtonProps } from './types'
```

#### 1.2 Naming Conventions

- **Components:** PascalCase (e.g., `UserProfile.tsx`)
- **Utilities:** camelCase (e.g., `formatDate.ts`)
- **Constants:** UPPER_SNAKE_CASE (e.g., `API_BASE_URL`)
- **Types/Interfaces:** PascalCase with descriptive suffixes (e.g., `UserProfileProps`, `ApiResponse`)
- **Test files:** Match source file name with `.test.tsx` or `.spec.tsx` suffix
- **E2E tests:** Descriptive names with `.spec.ts` suffix (e.g., `login-flow.spec.ts`)

### 2. **Test File Organization Requirements**

#### 2.1 Unit Tests (Co-located)

**REQUIRED:** Unit tests MUST be co-located with the source code they test.

```
src/components/Button/
├── Button.tsx
├── Button.test.tsx        # ✅ Co-located unit test
└── index.ts

src/hooks/useAuth.ts

import type { ApiResponse } from '@/types';

export interface User {
  id: string;
  name: string;
  email: string;
}

export const userService = {

    return response.data;

    return response.data;
  },

    const response = await apiClient.post<User>('/users', user);
    return response.data;
  },
};

  process.exit(1);
}

const directory = path.join(componentPath, componentName);

// Create directory
fs.mkdirSync(directory, { recursive: true });

// Component file
const componentContent = `import type { FC } from 'react'

interface ${componentName}Props {
  // Add props here
}

export const ${componentName}: FC<${componentName}Props> = (props) => {
  return (
    <div>
      <h1>${componentName}</h1>
    </div>
  )
}
`;

// Test file
const testContent = `import { render, screen } from '@testing-library/react'
import { ${componentName} } from './${componentName}'

describe('${componentName}', () => {
  it('should render correctly', () => {
    render(<${componentName} />)
    expect(screen.getByText('${componentName}')).toBeInTheDocument()
  })
})
`;

// Index file
const indexContent = `export { ${componentName} } from './${componentName}'
`;

// Write files
fs.writeFileSync(
  path.join(directory, `${componentName}.tsx`),
  componentContent
);
fs.writeFileSync(
  path.join(directory, `${componentName}.test.tsx`),
  testContent
);
fs.writeFileSync(path.join(directory, 'index.ts'), indexContent);

console.log(`✅ Component ${componentName} created successfully!`);
console.log(`📁 Location: ${directory}`);
```

### 17. **Scalability Considerations**

#### 17.1 When to Split Features

Split a feature into sub-features when:

- Feature directory has >15 files
- Feature has multiple distinct sub-domains
- Multiple teams work on the same feature

**Example:**

```
# Before (monolithic feature)
src/features/ecommerce/
├── components/ (30+ components)
├── hooks/
└── services/

# After (split into sub-features)
src/features/
├── products/
│   ├── components/
│   ├── hooks/
│   └── services/
├── cart/
│   ├── components/
│   ├── hooks/
│   └── services/
└── checkout/
    ├── components/
    ├── hooks/
    └── services/
```

#### 17.2 Micro-Frontend Preparation

Structure enables easy migration to micro-frontends:

```
# Each feature can become a micro-frontend
src/features/
├── auth/          → @app/auth-mfe
├── dashboard/     → @app/dashboard-mfe
└── products/      → @app/products-mfe
```
